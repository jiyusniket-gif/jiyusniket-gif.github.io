## 개요
 
오랜 취준생활에 생활비를 충당하기 위해 집가까운 신라호텔 발렛팀에 서무 아르바이트로 들어갔다. 
그중에 비정규 근무자들(헬퍼)들 근무 스케줄을 짜는 것이 내가 데일리로 처리할 업무였다. 기존에는 구글 폼으로 신청을 받고, 관리자가 엑셀로 수동 분배한 뒤, 카카오톡 단톡방에 결과를 올려 확인받는 방식으로 운영됐다. 이 흐름 전체를 Google Apps Script + Google Sheets 기반 웹앱으로 전환해, 신청자는 링크 하나로 신청/수정하고 관리자는
단일 화면에서 승인·배정·통보까지 처리하도록 만들었다. 현재 의사결정권자의 승인을 받고 테스트 운영 예정이다.
<br>

 ### 역할<br>
- 팀 규모: 1인 기획·설계·구현 (Claude Code와 페어 프로그래밍으로 반복 개발)
- 기여도: 아키텍처 설계 100%, 배정 로직 설계 100%, 프론트/백엔드 구현 방향 결정 및 검증 100%
<br>

## 접근 방식
![이미지 설명](content/posts/images/50/50-1.png)
<br>

- **시트 렌더링 → 웹앱 전면 전환** — 처음엔 "대시보드" 시트에 좌표를 찍어 표/차트를
  그리는 방식으로 시작했다. 결국 핸드오프 해야할 대상은 원래 일을 하던 사람들이었고, 이들은 엑셀에 더 익숙했기 때분이다. 그러나 구현 한계에 도달해 데이터는 시트에 그대로 두고, 그 위의 "화면" 레이어만 통째로 Apps Script 웹앱(HtmlService)으로 교체하는 방향으로 전환하되 최대한 직관적이고 단순하게 만들었다.<br>
- **0원 원칙** — 모든 기능을 Google Sheets(데이터 저장) + Apps Script(백엔드/웹앱) 안에서만 구현. 외부 결제·API 연동이 필요한 대안은 애초에 배제하고 최대한 단순하게 설계했다.
  '잘 만들어진 기계가 한정된 역할을 계속 수행하는 것'을 목표로 했다.<br>
- **관리자 트리거 원칙** — 자동화는 원칙적으로 관리자가 누르는 버튼에서 시작한다.
  완전 자동(시간 기반 트리거)은 되돌릴 위험이 없는 작업(지난 배정 결과 아카이빙)에만
  제한적으로 허용해, "관리자 모르게 뭔가 바뀌는" 상황 자체를 설계로 차단.<br>

- **3계층 데이터 구조** — 허브 파일(설정/블랙리스트/인물비고/주차관리, 순수 데이터만)
  + 템플릿 파일 + 매주 자동 생성되는 주간 파일(신청원장/TO/배정결과/수정요청큐/
  본사충원명단/변경이력). 지난 주 파일은 삭제하지 않고 그대로 남겨 자연스러운
  아카이브로 활용한다.<br>

  ![이미지 설명](content/posts/images/50/50-2.png)
<br>

- **승인 게이트 설계** — 이미 배정이 시작됐거나 확정 통보된 항목에 대한 신청/수정은
  즉시 반영하지 않고 관리자 승인 큐에 쌓이도록 설계해, "관리자가 모르는 사이 배정판이
  바뀌는" 상황을 방지.<br>

<br>

### 기술 스택
- 백엔드: Google Apps Script (V8 런타임), Google Sheets를 데이터베이스로 사용
- 프론트엔드: HtmlService 기반 단일 페이지 앱 — 프레임워크 없이 순수 JS/CSS,
  `google.script.run`으로 비동기 서버 호출
- 배포/버전관리: clasp (CLI 기반 Apps Script 배포)
- 데이터 모델: 허브 스프레드시트(설정/블랙리스트/인물비고/주차관리) + 주 단위로
  자동 생성되는 주간시트


### 주요 성과

| 항목 | Before | After |
|------|--------|-------|
| 신청 접수 | 구글 폼 제출 → 관리자가 수동 확인 | 링크 하나로 신청·수정, 필요 시 자동 승인 큐잉 |
| 배정 작업 | 엑셀로 수동 분배 | 배정 로직 3종(선착순/오전피크우선/균등배정) 원클릭 실행 + 드래그앤드롭 보정 |
| 결과 통보 | 카카오톡 단톡방에 수동 게시 | 시간순 정리된 통보 문구 자동 생성(0원 원칙상 발송은 여전히 수동 복사) |
| 관리자 화면 | 시트 좌표 기반, 반복적 렌더링 충돌 | 카드/배지/드래그앤드롭을 갖춘 웹앱 단일 화면 |
| 운영 비용 | 기존 수기 프로세스 | $0 (구글 계정 1개로 운영) |


### 경영상 개선된 점
- 헬퍼는 본인의 신청결과를 조회할 수 없고, 배정 전날 길게는 오후 17시까지 본인의 출근시간을 알 수 없었다. ->웹앱으로 실시간 배정상태를 조회할 수 있도록 개선했다.
- 실무진은 계속되는 업무중에 계속되는 문의를 처리해야 했다.-> 웹앱으로 인한 정보격차의 해소와 승인요청큐를 통해 불필요한 문의를 감소시켰다.
- 관리자와 실무진은 바로 다음날의 업무에만 치중했으나 주간대시보드를 통해 업무를 시각화함으로서 주단위 스케줄링이 가능해졌다. 이로인해 더 넓은 시각으로 업무를 예상할 수 있어졌다.
<br>

### 기술적 도전과 해결

**문제 1: 비동기 응답이 서버 완료 후에도 브라우저까지 안 돌아옴**
- 원인: Apps Script 웹앱은 sandbox iframe 안에서 서빙되는데, 응답이 크거나 서버
  실행이 오래 걸리는 호출에서 iframe↔서버 간 통신 채널 자체가 간헐적으로 응답을
  유실했다. 실행 로그상 서버는 4초대에 정상 완료됐는데도 브라우저는 응답을 못 받는
  경우가 재현돼, N+1 쿼리 제거 등 코드 최적화만으로는 해결되지 않는다고 결론지었다.
- 해결: 최초 로딩에 필요한 데이터는 `doGet` 단계에서 서버가 직접 계산해 HTML에
  스크립틀릿으로 심어, 그 통신 채널 자체를 타지 않게 했다. 이후의 재조회/새로고침은
  8초 타임아웃 후 자동 재시도(최대 3회)로 보완.
- 결과: 초기 로딩 안정성 확보, 재발 가능한 다른 화면에도 같은 패턴을 국소적으로
  재적용할 수 있도록 헬퍼 함수로 남겨둠.

**문제 2: 관리자 화면 탭 전환이 이유 없이 실패**
- 원인: sandbox iframe에서 브라우저 최상위 프레임 이동은 사용자 제스처의 동기 호출
  스택 안에서만 허용되는데, 비동기 콜백 안에서 URL을 알아내 이동을 시도하다 보니
  이 권한이 소실되는 구조적 문제였다.
- 해결: 주간/일일/설정 3개 화면을 물리적으로 별도 페이지로 두는 대신 단일 페이지
  앱으로 합치고, 탭 전환을 실제 페이지 이동이 아니라 같은 페이지 안에서 DOM을
  보였다 숨겼다 하는 방식으로 바꿔 문제 자체를 제거했다.
